# JT-75 Messaging event integration

`messaging.applications` consumes `application.submitted` through `pkg/events.Consume`.
The queue and its `.dead` queue use the shared JT-61 quorum topology, four-delivery
budget and 1/2/4 second backoff. The handler checks envelope metadata, typed payload
and all five payload UUIDs, normalizes participant IDs and rejects identical
applicant/employer IDs. Invalid events and participant conflicts are permanent;
database failures retry. The event ID claim and immutable participant projection
commit together. Redelivery of a claimed event is a no-op.

Migration `00004_events.sql` adds `processed_events` and `outbox_events`. Every
message insert stores a unique `message.sent` envelope in the same transaction.
Its approved payload contains only message, application and recipient IDs, with
producer `messaging` and the persisted message creation time. Existing messages
are not backfilled. Sending and listing retain existing authorization, validation,
oldest-first ordering and pagination.

One relay per process publishes pending rows in sequence, marks only after broker
confirmation and stops at the first failure. Failed connections reopen on the next
attempt. Failure to mark a confirmed publish can redeliver the same event ID;
consumers must deduplicate it. Published rows are retained. Multiple replicas can
publish a row twice, as with Offer/Review/Interview; this is at-least-once delivery.
Shutdown cancels and joins the consumer and relay before closing publisher and DB.

Compose already supplies the broker URL, database and dependency health checks, so
no Compose YAML change is required. If an old classic `messaging.applications`
queue exists, arrange migration with DevOps; do not delete queues automatically.
Events published before the durable queue existed are not replayed automatically.

Run from the repository root:

```sh
go generate ./services/messaging/internal/ports/...
gofmt -w services/messaging tests/contract/messaging_fixtures_test.go
go test ./services/messaging/... ./tests/contract
go vet ./services/messaging/... ./tests/contract
go test -tags=integration ./services/messaging/...
```

Testcontainers requires Docker. The tests use `postgres:17-alpine` and
`rabbitmq:4.1-alpine`. A writable `GOCACHE` can be set if the host cache is restricted.

Compose smoke verification (Docker Desktop arm64; use `GOARCH=amd64` on x86):

```sh
docker compose -f deploy/compose/docker-compose.yml up -d --build messaging
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o /private/tmp/jt75-smoke services/messaging/scripts/smoke.go
docker cp /private/tmp/jt75-smoke jobtrack-messaging-1:/tmp/jt75-smoke
docker compose -f deploy/compose/docker-compose.yml exec -T messaging /tmp/jt75-smoke
docker compose -f deploy/compose/docker-compose.yml exec -T --user root messaging rm /tmp/jt75-smoke
```

The smoke client uses container environment credentials, publishes a synthetic
application twice, sends through the public gRPC API with trusted metadata, and
observes the matching `message.sent` on RabbitMQ. It creates synthetic participant,
message, processed-event and outbox rows, and other subscribed services may receive
the synthetic application. Its temporary observation queue is removed on disconnect.
It does not delete application data or existing queues.
