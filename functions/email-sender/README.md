# Email sender (JT-77)

Stateless plain-text SMTP function called by Notification Dispatcher and Weekly
Summary. No database, broker consumer or external email provider is used.

## Agreed HTTP API

Shared caller reference: [email-sender HTTP contract](../../docs/deployment/email-sender-http-contract.md)
for Notification Dispatcher and Weekly Summary.

`POST /send-email`, `Content-Type: application/json`:

```json
{"recipient":"student@example.test","subject":"Application received","body":"Thank you for applying.\nTrack progress in JobTrack."}
```

Only one bare ASCII mailbox is accepted (no display names or recipient lists,
maximum 254 bytes). Subject is nonblank, at most 200 UTF-8 bytes, with no control
characters, including CR/LF. Body is nonblank, at most 65,536 UTF-8 bytes; CR, LF
and tab are allowed, other controls are rejected. Total request size is limited
to 131,072 bytes. Invalid UTF-8, unknown JSON fields and trailing JSON are rejected.
Headers are generated by the function; body line endings are normalized and SMTP
dot escaping is applied. The body uses quoted-printable encoding to bound SMTP
line lengths; non-ASCII subjects use MIME encoded words.

Responses have fixed safe text, except 204 which has no body:

| Status | Meaning |
| --- | --- |
| 204 | SMTP returned final 250 after DATA; accepted for delivery |
| 400 | Invalid JSON or invalid/missing fields |
| 405 | Non-POST request (`Allow: POST`) |
| 413 | Request exceeds size limit |
| 415 | Content-Type is not application/json |
| 503 | SMTP failed or timed out; caller may retry |

There is one SMTP attempt with an eight-second total deadline. Callers own retry
policy. Do not retry unchanged 4xx requests. A 503 may indicate a transient
failure or uncertain SMTP acceptance: SMTP can accept the email before its final
reply is lost or times out. Retrying 503 is not guaranteed duplicate-free. A lost
HTTP response after acceptance can also cause duplicates on retry. This stateless
API provides no deduplication. SMTP acceptance does not prove inbox arrival.
Logs contain only a fixed outcome and the validated intended recipient;
SMTP errors, subjects, bodies, sender addresses and credentials are never logged.

Timeouts are sequential: HTTP headers have a 5 s limit and the entire request
read (including headers/body) has a 10 s limit. After validation, SMTP has a
separate 8 s context budget covering DNS/TCP connection, greeting, commands,
DATA and its final acceptance reply. The connection deadline and cancellation
watcher interrupt SMTP I/O on timeout or request-context cancellation.
The HTTP write deadline is 22 s from completion of the headers, covering the
remaining read budget, SMTP and 4 s response margin. Knative's request timeout
is 25 s. Callers need a timeout above the full request budget if they want to
allow all of this time; their configuration is outside JT-77.

On SIGTERM/SIGINT, the HTTP server stops accepting requests and drains active
requests for up to 22 s without cancelling them merely because shutdown began.
Compose gives this container 25 s before forced termination. A request still
active after the bounded shutdown grace can be interrupted by process exit.
The SMTP 8 s budget and validation/response behavior are unchanged.

Regression tests use a real local HTTP listener and fake SMTP server with
scaled HTTP deadlines: a delayed body plus delayed DATA acceptance reproduces
loss of the response with the old deadline, and returns 204 with the aligned
budget. Additional tests cover a stalled DATA reply, rejection after DATA,
and shutdown waiting for an in-flight delivery. No live email is needed for
these tests. Production-budget assertions guard the 10/8/22 s relationship.

`GET /healthz` reports process health; `GET /metrics` exposes
`jobtrack_email_sender_up 1` in Prometheus text format. Neither probes SMTP.

## Configuration

| Variable | Meaning |
| --- | --- |
| SMTP_ADDR | Required host:port; Compose and manifest use `mailpit:1025` |
| SMTP_FROM | Required bare sender address; deployment default `noreply@jobtrack.test` |
| HTTP_PORT | Listener port, default 8080 |
| SERVICE_NAME | Deployment convention: `email-sender`; logs use this fixed name |
| EMAIL_SENDER_FROM | Compose override for SMTP_FROM |
| EMAIL_SENDER_IMAGE | Compose image override, default `jobtrack-email-sender:local` |

Invalid SMTP address, sender or listener port prevents startup. SMTP is plaintext,
unauthenticated and intended for Mailpit on the private project network. There
are no SMTP credentials, TLS settings or external-provider support in JT-77.
No INTERNAL_TOKEN is needed. The HTTP API is internal and has no user authentication.

## Run and verify

From the repository root, with the existing Compose `.env` configured:

```sh
go test ./functions/email-sender/...
go vet ./functions/email-sender/...
go test ./...
go vet ./...
docker compose -f deploy/compose/docker-compose.yml --profile functions config --quiet
docker compose -f deploy/compose/docker-compose.yml --profile functions up -d --build email-sender
```

The function has no published host port. Send from another container on the
Compose network, for example using Mailpit's container if wget is available:

```sh
docker compose -f deploy/compose/docker-compose.yml exec mailpit wget -S -O- \
  --header='Content-Type: application/json' \
  --post-data='{"recipient":"student@example.test","subject":"JT-77 test","body":"Hello from JobTrack."}' \
  http://email-sender:8080/send-email
```

If that image lacks wget, use an existing HTTP-capable container on the same
network. Confirm 204, then open `http://localhost:8025` and inspect recipient,
subject and plain-text body. Also inspect function logs for safe outcomes.
This live Mailpit check must be completed during review; automated tests use a
fake SMTP server, not Mailpit.

For a local process example (host Mailpit SMTP port 1025):

```sh
SMTP_ADDR=localhost:1025 SMTP_FROM=noreply@jobtrack.test go run ./functions/email-sender/cmd/server
# In another terminal:
curl -i http://localhost:8080/send-email -H 'Content-Type: application/json' \
  -d '{"recipient":"student@example.test","subject":"JT-77 test","body":"Hello."}'
```

## Knative deployment

Build from repository root, load into the existing k3d cluster, then apply:

```sh
docker build -f functions/email-sender/Dockerfile -t jobtrack-email-sender:local .
k3d image import jobtrack-email-sender:local -c <existing-cluster-name>
kubectl apply -f deploy/knative/email-sender.yaml -n <project-namespace>
kubectl get ksvc email-sender -n <project-namespace>
```

Replace angle-bracket placeholders with existing deployment names. The manifest
uses scale-to-zero, port 8080 and an HTTP readiness probe. Mailpit must resolve as
`mailpit` in that namespace and accept TCP 1025. Invoke the Knative service URL
from the calling functions inside the cluster; do not add a gateway route.

Test case traceability: [JT-77 test cases](../../docs/testing/jt-77-test-cases.md).
